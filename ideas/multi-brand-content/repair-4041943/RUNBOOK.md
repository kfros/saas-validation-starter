# Multi-brand: исправление evidence и повторный аудит

База: `4041943510d75728079d02606ade13a6c6d187d4`.

Этот комплект содержит задания и launch prompts. Он ещё не исправляет raw,
не выполняет новое исследование и не меняет оценку идеи. Цель запусков —
получить точные исходные записи, закончить недостающий Workflow и проверить
решающие свидетельства в обновлённом наборе.

## 1. Подготовить рабочую ветку

Останови агентов, которые могут писать в этот репозиторий. Сначала выполни:

```bash
git status --short
```

Продолжай, когда рабочая директория чистая. Если есть нужные незакоммиченные
изменения, сначала сохрани их отдельным коммитом. Ничего не удаляй и не применяй
`reset --hard`. Более поздние результаты на другой ветке сохранятся; этот ремонт
отдельно воспроизводит состояние `4041943`.

В терминале человека из корня репозитория:

```bash
git switch -c validation/multi-brand-evidence-repair 4041943
git am /path/to/multi-brand-evidence-repair.patch
python scripts/check_multibrand_stage1.py preflight
```

Заменить `/path/to/` фактическим путём к скачанному patch; путь с пробелами
заключить в кавычки. Если ветка с этим именем уже существует, используй новое
свободное имя. Если Git сообщает, что patch уже применён, не накладывай его второй
раз: проверь наличие файлов ниже. При конфликте остановись и проверь базу;
не разрешай его автоматической заменой чужих результатов.

Команды Git выполняешь ты. Research-агентам они не разрешены. Их единственные
команды терминала — готовый checker с фазой, указанной в конкретном prompt.

## 2. Выполнить четыре адресных запуска

Каждая строка — **новый conversation**, рекомендуемый уровень модели **High**.
Запускай последовательно, чтобы не умножать расход квоты. Читай Markdown-файл
prompt и вставляй только содержимое блока `text` после вызова указанных скиллов.
Имена `.agent/skills` в единственном числе сохранены.

Все prompt-файлы лежат в `prompts/multi-brand-content/repair-4041943/`.

| Порядок | Скиллы | Prompt | Задача и разрешённая папка записи |
| --- | --- | --- | --- |
| 1 | `/browser` + `/wtp-research` | `01-repair-wtp.md` | Проверить десять WTP-записей; `raw/wtp/`. |
| 2 | `/browser` + `/pain-mining` | `02-repair-pain.md` | Исправить атрибуцию боли, сохранить подтверждённые проблемы; `raw/pain/`. |
| 3 | `/browser` + `/skeptic-research` | `03-repair-skeptic.md` | Проверить цитаты и границы отрицательных выводов; `raw/skeptic/`. |
| 4 | `/browser` + `/workflow-mapping` | `04-complete-workflow.md` | Исправить пять старых записей и закончить недостающий поиск; `raw/workflow/`. |

Подробный список ошибок, ID и источников находится в
[repair-tasks.md](repair-tasks.md). Он задаёт вопросы для проверки, а не заменяет
источники. WTP/Pain/Skeptic перепроверяют существующие страницы. Workflow также
ищет оригинальные публичные профили и описания процессов; 3–5 примеров — ориентир,
не обязательная квота и не доказательство размера рынка.

Каждый агент сохраняет все старые ID, оставляет raw в `PENDING`, обновляет отчёт
своего трека и создаёт `repair-log.md`: что проверено, что изменено, что заблокировано.
Все поля проверяются вместе: исправить observation и оставить неподтверждённую
цитату, ICP, роль или деньги нельзя.

Если оригинальная страница недоступна, агент не исправляет факты по этому списку
или памяти. Он сохраняет запись и помечает задачу `BLOCKED`. Если снова предлагает
`python -c`, чтение `.gemini/antigravity/brain` или самодельный scraper, отклони
именно это действие и напомни allowlist из prompt. Разрешать его ради продолжения
исследования не требуется.

Примерно 45 минут — бюджет работы одной сессии, а не обязательное время ожидания.
При исчерпании квоты/бюджета допустим `PARTIAL`. Не удаляй разговоры и результаты,
не заставляй агента добирать количество записей. Для продолжения используй тот же
launch prompt: он начинает с текущих файлов и журнала, сохраняет ID и не добавляет
дубликаты. В журналах должны быть видны даты и результаты проверок разных сессий.

## 3. Зафиксировать raw перед аудитом

После остановки всех четырёх агентов проверь из корня репозитория:

```bash
python scripts/check_multibrand_stage1.py raw-all
git diff --stat
git diff --check
```

`raw-all` должен завершиться успешно. Он допускает честный `PARTIAL` трека с
успешной структурной проверкой; это не означает завершённую проверку источников.
В каждом из четырёх треков должны быть `repair-log.md` и актуальный `run-status.json`.
Если checker не проходит, верни точную ошибку владельцу трека до запуска Auditor.

Изменения исследований должны затрагивать только четыре разрешённые raw-папки.
Если агент изменил methodology, скрипты, hypothesis или чужие результаты,
сначала разберись с этими изменениями. После проверки сохрани checkpoint:

```bash
git add ideas/multi-brand-content/raw/wtp ideas/multi-brand-content/raw/pain ideas/multi-brand-content/raw/skeptic ideas/multi-brand-content/raw/workflow
git commit -m "Repair multi-brand evidence and resume workflow"
```

Если изменений нет, новый коммит не нужен. Не запускай raw-агентов во время аудита.

## 4. Повторить аудит

Новый conversation, **High**: `/browser` + `/evidence-audit`, затем
`prompts/multi-brand-content/repair-4041943/05-reaudit.md`.

Auditor заново собирает все текущие raw-ID и сначала проверяет изменённые,
заблокированные и решающие записи. Для полного свежего аудита он затем проверяет
остальные оригиналы. Старые `VERIFIED` сами по себе не служат основанием сохранить
статус. У каждой проверки должна быть дата и связь URL → ID.

Если работа прервалась, обновлённый набор сохраняет все ID, непроверенное остаётся
`PENDING`, audit-summary явно говорит `PARTIAL`. При продолжении можно использовать
проверки из журнала **этого** repair-аудита для неизменившихся raw, сохранив их даты.
Непроверенные статусы старого аудита `4041943` так переносить нельзя.

Auditor пишет только в `ideas/multi-brand-content/evidence/`. Он не исправляет
сырой observation ради `VERIFIED` и не ищет новые источники. Если ошибка осталась,
он фиксирует её и адресную задачу владельцу raw. Возвращаться к исследованию нужно
по конкретному незавершённому вопросу; бесконечный цикл перезапусков не требуется.

Новые профили не доказывают недостающие характеристики чужих Reddit-авторов.
`UNKNOWN` по scope может остаться даже после точной проверки текста. Это не ошибка
формата и не отрицательное рыночное свидетельство.

## 5. Сохранить и принести результат

После завершения Auditor:

```bash
python scripts/check_multibrand_stage1.py audit
git diff --check
git diff --stat
git add ideas/multi-brand-content/evidence
git commit -m "Reaudit repaired multi-brand evidence"
git push -u origin validation/multi-brand-evidence-repair
git rev-parse HEAD
```

Если выбрано другое имя ветки, подставь его в `git push`. Эти команды снова
выполняет человек. Проверь перед коммитом, что новые изменения Auditor находятся
только в `evidence/`. Если нечего коммитить, этот шаг пропускается.

Пришли имя ветки и SHA после push. Для разбора нужны:

- `evidence/evidence.jsonl`;
- `evidence/audit-summary.md`;
- `evidence/high-impact-review.md`;
- `evidence/scope-map.json`;
- обновлённые четыре raw-трека с `repair-log.md`, `run-status.json` и отчётами,
  особенно `raw/workflow/workflow-map.md` и `icp-candidates.md`.

Пути в этом списке относительны к `ideas/multi-brand-content/`.

Judge пока не запускаем. После изменения raw/audit существующие
`output/stage1-report.md` и `scorecard.json` остаются историческими результатами
базы `4041943`; они не описывают исправленный набор.

Сначала разбираем, что теперь подтверждено и какие вопросы ещё открыты. Возможное
изменение правил допуска к интервью — отдельное решение с новой версией
методологии, применяемой последовательно к идеям. Этот комплект не ослабляет gates
и не обещает PASS или переход к Stage 2.
